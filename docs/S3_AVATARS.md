# Аватары в S3 (диски media_local / media_s3)

Краткая инструкция по подключению S3-хранилища Timeweb для аватаров и переносу
существующих локальных файлов. Затрагивает только аватары `users` и `clients`;
`FILESYSTEM_DISK`, существующие диски `local`/`public`/`s3` и AWS_*-переменные
не меняются.

## Как устроено

- Для аватаров два конкретных диска (`config/filesystems.php`):
  `media_local` (локально, `storage/app/public/avatars/`, URL вида
  `/storage/avatars/...`) и `media_s3` (S3, публичный URL из
  `MEDIA_PUBLIC_URL`). Единая точка записи/замены/удаления —
  `App\Services\Avatars\AvatarStorageService` (его используют все четыре
  писателя: `SettingsController`, `TelegramWebhookHandler` ×2,
  `clients:sync-avatars`).
- `MEDIA_DRIVER` выбирает только диск, на который пишутся **новые** аватары:
  по умолчанию `local` → `media_local`, `s3` → `media_s3`. Сам диск и его
  конфигурация от режима не зависят — переключение не меняет смысл уже
  сохранённых ссылок.
- В БД рядом с `avatar_url` хранятся nullable `avatar_disk`/`avatar_path` —
  точная ссылка на файл с конкретным хранилищем (`public`, `media_local`
  или `media_s3`). Существующие локальные и S3-файлы читаются, переносятся
  и удаляются именно со своего backend, даже после смены `MEDIA_DRIVER`.
  Старые записи разбираются из `/storage/...`-URL; внешние URL никогда
  не читаются и не удаляются.
- Имена объектов случайные (40 символов), без телефона/Telegram ID/имени.
- Замена: записать новый файл → условное обновление БД (CAS по наблюдавшемуся
  `avatar_url`) → удалить старый принадлежащий приложению файл.

## Переменные окружения (без секретов)

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `MEDIA_DRIVER` | `local` | `local` или `s3`. Определяет, на какой из дисков (`media_local`/`media_s3`) пишутся **новые** аватары; `s3` — только после полной настройки ниже. |
| `MEDIA_S3_KEY` | — | Access Key пользователя бакета (напр. `irsi-app-media`). Секрет, в репозиторий не попадает. |
| `MEDIA_S3_SECRET` | — | Secret Key того же пользователя. Секрет. |
| `MEDIA_S3_REGION` | `ru-1` | Регион Timeweb (из панели/документации). |
| `MEDIA_S3_BUCKET` | — | Имя бакета, например `irsi-media`. |
| `MEDIA_S3_ENDPOINT` | — | `https://s3.twcstorage.ru` |
| `MEDIA_S3_PATH_STYLE` | `true` | Timeweb использует URL вида `endpoint/bucket/key` (см. «Описание принципов работы с S3»), поэтому path-style. |
| `MEDIA_PUBLIC_URL` | — | Публичный base URL бакета. **Не угадывать** — см. ниже, как получить. |

`MEDIA_PUBLIC_URL` обязателен при `MEDIA_DRIVER=s3`: без него сервис не
сохранит аватар (падение до записи в БД, старый аватар не теряется), команда
переноса откажется работать, а публичный GET при пробе S3 (ниже) не пройдёт.
Для самой пробы S3-диска `MEDIA_DRIVER` переключать не нужно.

### Как получить `MEDIA_PUBLIC_URL`

1. В панели Timeweb → «Хранилище S3» → бакет `irsi-media` → вкладка
   «Дашборд»/настройки: там же лежат реквизиты подключения и адрес
   публичного доступа (для публичного бакета авторизация для чтения не нужна).
2. Либо фактически: загрузить пробный объект и открыть его в браузере —
   базовая часть адреса до ключа объекта и есть `MEDIA_PUBLIC_URL`.
   Согласно документации Timeweb путь выглядит как
   `https://s3.twcstorage.ru/<bucket>/<key>`, но **подтвердите это на своих
   данных** (curl/браузер) и впишите полученный base URL целиком,
   без ключа объекта и без завершающего `/`.

## Порядок выкладки

1. `composer install` — подтянет `league/flysystem-aws-s3-v3` и `aws/aws-sdk-php`
   (адресная зависимость, без обновления остальных пакетов).
2. `php artisan migrate` — создаёт `avatar_disk`/`avatar_path` в `users` и
   `clients` и заполняет их для существующих локальных `/storage/...`-записей.
3. Задать `MEDIA_*` переменные (ключ/секрет/бакет/endpoint/регион/`MEDIA_PUBLIC_URL`),
   оставив `MEDIA_DRIVER=local`, затем `php artisan config:cache`.
4. **Проверка живого S3 без глобального переключения приложения**. Диск
   `media_s3` сконфигурирован независимо от `MEDIA_DRIVER`, поэтому пробу
   выполняйте, оставаясь на `local`: приложение продолжает работать как
   раньше, меняются только объекты под префиксом `avatars/`.

   Порядок проверки объекта: **запись → чтение → публичный GET → удаление**.

   Запись и чтение (tinker):

   ```bash
   php artisan tinker
   >>> Storage::disk('media_s3')->put('avatars/_probe.txt', 'probe');   # запись
   >>> Storage::disk('media_s3')->get('avatars/_probe.txt');            # чтение: "probe"
   >>> Storage::disk('media_s3')->url('avatars/_probe.txt');            # публичный URL объекта
   ```

   Публичный GET — в отдельном терминале, **до удаления объекта**
   (код 200 подтверждает запись и базовый `MEDIA_PUBLIC_URL`):

   ```bash
   curl -I '<публичный URL объекта из tinker>'    # напр. https://s3.twcstorage.ru/irsi-media/avatars/_probe.txt
   ```

   Удаление (тот же tinker-сеанс, после успешного GET):

   ```bash
   >>> Storage::disk('media_s3')->delete('avatars/_probe.txt');
   ```

   При ошибке `AccessControlListNotSupported` или 403 сверьте
   `MEDIA_S3_PATH_STYLE`, регион и тип бакета («Публичный»).

5. Включить `MEDIA_DRIVER=s3` и пересобрать конфиг:

   ```bash
   php artisan config:cache
   ```

   Конфигурация читается процессом при старте, поэтому после изменения
   production-конфига перезапустите долгоживущие процессы, использующие
   конфигурацию: воркеры очереди (`php artisan queue:restart`), Reverb
   (`php artisan reverb:restart`) и остальные демоны под супервизором/Octane —
   иначе они продолжат писать новые аватары на прежний диск.
6. Перенос:

   ```bash
   php artisan avatars:migrate-to-s3 --dry-run   # только список, без записей в БД/S3 и без удалений
   php artisan avatars:migrate-to-s3             # копирование + проверка размера и SHA-256 чтением из S3
   ```

   Реальный запуск: копирование → чтение объекта из S3 → сверка размера и
   SHA-256 → условное обновление строки, только если исходный аватар не
   изменился. Локальные оригиналы **не удаляются**. Повторный запуск безопасен
   (уже перенесённые записи пропускаются, существующие чужие объекты не
   перезаписываются). Итоги (`migrated/already migrated/conflicts/missing/
   verification mismatches/S3 errors`) печатаются в конце; ненулевой exit —
   при ошибках и конфликтах, их нужно разобрать и повторить запуск.
7. Проверка после переноса: загрузить аватар в UI, убедиться, что
   `avatar_url` открывается (https://…irsi-media…), аватар отображается
   в интерфейсе; локальные файлы в `storage/app/public/avatars/` на месте.

## Откат (с учётом уже созданных S3-аватаров)

- **Откат поведения без отката кода**: выставить `MEDIA_DRIVER=local`,
  повторить `config:cache` и перезапустить долгоживущие процессы (см. шаг 5) —
  новые аватары снова пишутся на `media_local`. Записи с
  `avatar_disk=media_s3` при этом продолжают разрешаться на S3: замена или
  удаление такого аватара обращается к бакету, а не к локальному диску;
  сохранённые S3-URL остаются рабочими, пока бакет публичен. Переключение
  режима меняет только цель новых загрузок и не переводит существующие
  файлы между хранилищами — по ним всё решает сохранённый `avatar_disk`.
- **Полный откат кода** (`git revert`): колонки `avatar_disk`/`avatar_path`
  в БД безвредны (старый код их игнорирует), `avatar_url` со старых
  перенесённых записей остаётся абсолютным S3-URL и продолжает работать при
  публичном бакете. Новые загрузки уйдут на `public`-диск.
- **S3-объекты**: автоматического cleanup нет. Перед ручным удалением
  объектов убедиться, что ни одна запись не ссылается:
  `SELECT id, avatar_url FROM users WHERE avatar_url LIKE '%s3.twcstorage.ru%';
  SELECT id, avatar_url FROM clients WHERE avatar_url LIKE '%s3.twcstorage.ru%';`
  Удалять только объекты в префиксах `avatars/`.
- **Локальные оригиналы не удалялись** — они же и есть резерв для отката.

## Ограничения

- Тесты используют `Storage::fake`/локальные диски; живой Timeweb S3
  тестами не вызывался — реальная проверка выполняется только по шагам выше.
- Портфолио, CDN и бэкапы не реализованы; `cleanup`-команды для локальных
  оригиналов и S3-объектов нет.
- Команда переноса на production в рамках этого изменения не запускалась.
