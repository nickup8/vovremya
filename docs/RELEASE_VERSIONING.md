# Версионирование релизов

Номер релиза — **пользовательская версия** приложения в формате semver
(`MAJOR.MINOR.PATCH`), например `1.1.0`. Это отдельное значение от
технического git SHA сборки.

## Источники значений

- **Номер релиза** фиксируется в репозитории в отслеживаемом файле
  `VERSION` — единственный источник. Вручную номер не дублируется в
  других файлах исходного кода. deploy.sh при выкладке пишет его в
  серверный `.env` как `APP_VERSION`.
- **Git SHA** определяется при выкладке: deploy.sh выполняет
  `git rev-parse HEAD` и записывает полный SHA в `.env` как
  `APP_BUILD_SHA`. SHA не является версией и в `APP_VERSION` не пишется.
- Локально без этих переменных в `.env` действуют значения по умолчанию:
  версия — содержимое файла `VERSION`, сборка — `dev`.

Один релиз может включать несколько коммитов: номер меняется один раз при
подготовке релиза на production, SHA у каждого развёрнутого коммита свой.

## Когда менять номер

| Изменение | Уровень | Пример |
|---|---|---|
| Совместимые исправления и обновления безопасности | **patch** | `1.1.0` → `1.1.1` |
| Новые совместимые функции | **minor** | `1.1.0` → `1.2.0` |
| Несовместимые изменения публичного API/интеграций | **major** | `1.1.0` → `2.0.0` |

Номер меняется **при подготовке релиза на production**: правится файл
`VERSION` в том же релизе (обычно одним из последних коммитов перед
выкладкой). Git-тег `vX.Y.Z` ставится на проверенный коммит после ревью и
слияния.

## Где отображается и сохраняется

- В интерфейсе (сайдбар суперадминки) показывается пользовательский номер
  релиза; полный SHA в интерфейс не выводится.
- В manifest резервной копии БД сохраняются оба значения раздельно:
  `app_version` (номер релиза) и `app_build_sha` (полный git SHA) —
  см. [DB_BACKUPS.md](DB_BACKUPS.md).
